## Implemented lifecycle map

1. Authenticate and establish active account/role. Build group and obtain department approval; assignment confirmations and the group flow control title eligibility (`research-group-flow.php`). Database persistence and denial paths remain unexecuted.
2. Title approval must satisfy `status`, `coordinator_status`, and `crad_status` = Approved, with nonempty adviser/coordinator/CRAD signatures (`cradValidTitleApprovalWhereSql`). CRAD approval updates require pending CRAD review and coordinator approval (`register-proposal.php`). Rejection/revision and resubmission need role fixtures to verify.
3. Student submits sequential chapters and progress; adviser validates/evaluates and can request revisions. The previous-chapter submission gate is shared by UI eligibility and handler according to the implementation and existing regression test. Exact acceptance semantics must remain those of the code, not a newly invented rule.
4. Group panel request: Draft → Submitted → Under Review → Approved → Scheduled → Completed; Under Review → Rejected → Submitted is the resubmission branch. Required attachments are manuscript and signed approval sheet; transitions write request history (`panel-applications.php`). This request status chain is separate from actual defense scheduling.
5. Assign panel/chair and schedule defense subject to panel-size, availability and conflict checks. Rescheduling records a reason and history (`defense-reschedule.php`). Full creation/rescheduling persistence and notification effects remain unverified.
6. Manuscript review uses Submitted / Under Review / For Revision / Approved; approval eligibility checks evaluation state. Final-defense revision cycles use Needs Revision / Under Review / Compliant, with evidence and submission gates (`final-phase-helpers.php`). Final manuscript approval is a separate record.
7. Receipt/clearance processing has Research 1 and Research 2 stages: upload validation/storage → local OCR → reference parsing → payment row/member references → review and clearance updates (`research-clearance-payment.php`). This is not assumed to precede every manuscript workflow; `rcpCanUploadStage()` contains its own stage eligibility rules. Only text parsing was executed.
8. Publication creation requires the signed valid title predicate and Approved final manuscript, then creates Draft. Management exposes Draft / For Publication / Published / Archived. Repository accepts For Publication / Published / Archived filters and requires CRAD/coordinator authorization. Public visibility and search are not established by this management page alone.
9. Grant approval is a parallel six-step chain, not assumed mandatory for all research. Returns, final funding, milestones, documents and output depend on grant APIs/helpers. Notifications and audit effects require transactional runtime verification.

## Baseline defects and risks

### D-001 — Medium: numeric OR values discarded (CRAD-OCR-001)

Confirmed by executed pure parser test. Preconditions: explicit numeric receipt label, no other candidate. Reproduction and actual/expected appear above. Root cause: `rcpIsPlausibleReference()` rejects long numeric tokens and ultimately requires letters plus digits, even for label-adjacent OR candidates. Proposed fix: recognize explicit official-receipt labels separately and preserve numeric strings/leading zeros while excluding date, amount and student fields. Do not relax arbitrary fallback tokens globally. Real supported receipt layouts still need validation.

### D-002 — High: student identifier promoted to receipt reference (CRAD-OCR-004)

Confirmed parser misclassification; no live payment approval was tested. Root cause: generic standalone alphanumeric fallback accepts `ABC123456` without requiring receipt-label context; parser takes the first candidate without an uncertainty result. Proposed fix: exclude student/invoice fields, require supported receipt context, and return uncertainty for manual verification. This severity reflects incorrect financial evidence association, not a demonstrated unauthorized payment action.

### R-001 — High impact static risk: connection-time evaluation deletion

Source confirms connection → cleanup → DELETE in `modules/crad/config/config.php`. The official registry predicate includes current title signatures/approvals and assignment requirements; records outside it can lose evaluation rows when a connection opens. Runtime deletion and affected record counts were deliberately not tested. Review intended retention requirements; move destructive reconciliation to an explicit controlled maintenance operation with preview and recovery. Do not classify any real records as corrupt without evidence.

### R-002 — Medium static risk: publication creation race

`publication-create.php` checks NOT EXISTS then separately INSERTs. The deployed-schema source has only nonunique `idx_pub_group`, not a unique group constraint. Concurrent requests could both pass the check. This is a source-supported risk, not an executed concurrency failure. Confirm the intended one-record-per-group rule, then use database uniqueness and handle duplicate insertion safely after checking existing duplicates in staging.

### R-003 — Medium static risk: analysis can run through GET without endpoint CSRF check

The AI endpoint defaults action to analyze, accepts GET action, and contains no request-method restriction or explicit CSRF verification before provider execution and saving analysis. It does check adviser role and submission ownership. Session cookies use SameSite Lax, which is not a replacement for protecting state-changing GET actions. Browser exploitability and actual provider spend were not tested. Require POST and the established CSRF mechanism for analyze; preserve read-only latest retrieval separately.

### R-004 — Medium test safety risk: split database configuration

The Python SQL helper and PHP account helper do not share the same test override mechanism. A test DB override alone could mix fixture creation and assertions across databases. Confirm both target connections and application HTTP target before any mutating suite. Cleanup of test accounts is not proof that other workflow writes or notifications are isolated.
